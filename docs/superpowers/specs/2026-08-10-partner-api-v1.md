# Lazybee Partner API v1

*Spec, 2026-08-10. Approved by Mark in brainstorm (scope: two-way plus webhooks; keys: manual issue; rates: channel-resolved; hosting: single Vercel catch-all).*

## Why

Aggregator platforms want to ingest our inventory and send us tenants. The first concrete request (Pranjal Singh's team, email 10 Aug 2026) asks for photos, booking information, availability, pricing, amenities, descriptions and property URLs. We are not building them a bespoke feed. We are publishing a public, versioned partner surface over the listing-distribution layer that already exists on `feat/channel-pricing` (`listing_profiles`, `listing_channels`, `listing_placements`, `room_calendar`, channel pricing arithmetic in `supabase/functions/_shared/channelPricing.js`). The API speaks our internal vocabulary, not the requester's, because it genuinely is our internal contract exposed over HTTP.

## Product decisions (locked)

1. **Scope: two-way plus webhooks.** Read endpoints for the full inventory, a write endpoint for partners to push booking requests, and webhook subscriptions that push change events to partners.
2. **Keys: manually issued.** We insert a key per partner and email it. The docs page explains auth and gives `partners@lazybee.sg` as the request-access route. No self-serve signup in v1.
3. **Rates: channel-resolved.** A partner's key returns prices resolved through the channel pricing layer: base `rooms.price_monthly` when their channel row has no commission configured, their grossed-up contracted rate the moment it does. Margin math is never exposed.
4. **Hosting: one Vercel catch-all in this repo.** `api/v1/[...path].js` routes every partner endpoint. The dead `api/send-room-request.js` (broken `createTransporter` call, zero frontend callers) is deleted in the same change, so the function count stays at exactly 12, the Vercel Hobby cap.

## Naming map (theirs vs ours)

| They asked for | We expose |
|---|---|
| Property and room-level photos | `media` arrays on properties and listings |
| Tenancy / booking information | `calendar` windows plus `booking-requests` (their own only) |
| Availability data | `GET /v1/listings/{code}/calendar`, `available_from` on listings |
| Pricing / rates | `rate_card` object |
| Amenities | `features` |
| Property and room descriptions | `profile.title`, `profile.description` |
| Property URLs | `links` (canonical page, booking page) |

## Surface

Base URL `https://lazybee.sg/api/v1`. JSON only, ISO 8601 dates, SGD amounts, cursor pagination on list endpoints, `updated_at` on every resource.

| Endpoint | Behaviour |
|---|---|
| `GET /v1/ping` | Auth sanity check; returns partner name and scopes |
| `GET /v1/properties` | The 3 buildings: slug, profile, media, features, links, listing count |
| `GET /v1/properties/{slug}` | One building |
| `GET /v1/listings` | All lettable rooms; filters: `property`, `available_from`, `max_rate` |
| `GET /v1/listings/{code}` | One room: profile, media, features, rate_card, links, next open window |
| `GET /v1/listings/{code}/calendar` | Date windows, each `open` or `unavailable`. Nothing else |
| `POST /v1/booking-requests` | Partner submits a lead or booking request; idempotency key honoured |
| `GET /v1/booking-requests/{id}` | Status of their own requests only: `received`, `in_review`, `confirmed`, `declined` |
| `POST /v1/webhooks` | Register endpoint URL plus event types; returns signing secret |
| `GET /v1/webhooks`, `DELETE /v1/webhooks/{id}` | List and remove their subscriptions |

### Data sources

- Properties and listings read `listing_profiles` (title, description, jsonb fields) joined to `rooms` and properties. Media URLs come from the same storage the site uses.
- `rate_card` is `{ monthly_rate, deposit, min_stay_months, utilities }`, with `monthly_rate` computed per-partner via `channelPricing.js` (gross-up rule: base is net, commission-bearing channels list higher).
- Calendar windows derive from `room_calendar` rows with `status = 'ACTIVE'` and `blocks = true`, collapsed and merged into date ranges. Kind, source, notes and any tenant identity NEVER appear in output; a window is only ever `unavailable`. `available_from` reuses the min-window derivation shipped in `20260810000004_next_available_min_window.sql`.
- Rooms whose channel placement is disabled, and channels with `enabled = false`, get nothing: the existing kill switch gates the whole API per partner.

## Partner identity and auth

A partner IS a `listing_channels` row with `mechanism = 'api'` and their commercial terms (`commission_pct` or `commission_months`, `gross_up`, `fee_fixed`) on the row. New table `channel_api_keys`: `id`, `channel_id` (fk), `key_hash` (sha256), `label`, `rate_limit_per_min`, `created_at`, `last_used_at`, `revoked_at`. Header: `Authorization: Bearer lzb_live_<random>`. Keys are generated by us, shown once, stored hashed. Rate limiting is enforced per key at the router; mechanism chosen at plan time (limits live on the key row either way). All requests logged minimally (key, route, status, ms) for audit.

## Booking requests

`POST /v1/booking-requests` accepts `{ listing_code, move_in, duration_months, applicant: { name, email, phone, nationality? }, note?, idempotency_key }`. Effect: one row in a new `booking_requests` table (channel-attributed), one `room_calendar` row with `kind = 'ENQUIRY'`, `blocks = false`, `source = <channel slug>`, `auto_created = true` (per Mark's rule: an enquiry records but never blocks), and a notification email to admin@lazybee.sg via Resend (the portal's existing transport; this replaces the broken nodemailer path). Status changes are made by us and fire the `booking_request.updated` webhook. This endpoint supersedes `send-room-request` entirely.

## Webhooks

Events: `listing.calendar.updated`, `listing.rates.updated`, `listing.profile.updated`, `booking_request.updated`. Flow: Supabase database webhooks on the underlying tables call `POST /api/v1/internal/dispatch` (guarded by a shared secret env var, not a partner key). The dispatcher resolves affected listings, writes one delivery row per subscription, attempts delivery immediately with an HMAC-SHA256 signature header (per-subscription secret), and records the outcome. Failed deliveries are retried by a scheduled sweep (pg_cron on the database calling the same dispatch route). No client polling anywhere. Delivery log retained 30 days.

## Docs page

`lazybee.sg/developers`, a prerendered static page in the site's own design system. Sections: overview, authentication, quickstart (curl), endpoint reference with example responses, webhook events and signature verification, rate limits, request access (`partners@lazybee.sg`). Versioned plainly as v1. No fabricated changelog and no invented dates: maturity is conveyed by completeness, not by fiction.

## Function budget

Before: 12 functions including dead `send-room-request.js`. After: still 12 (`api/v1/[...path].js` in, `send-room-request.js` out). No rewrite alias needed: the old path has zero callers.

## Out of scope for v1

Self-serve key management, partner dashboards, OAuth, per-channel outbound push mappers (the worker contract covers those), availability import FROM partners, multi-currency, and any exposure of tenant identity or inter-channel data.

## Success criteria

1. A partner with a key can, without talking to us: list properties and listings with media, features, profiles and links; read per-listing calendars; read their channel-resolved rate card; submit a booking request and poll its status; register a webhook and receive signed events on calendar, rate, profile and booking-request changes.
2. Function count is exactly 12 after merge; `vercel build` passes.
3. Zero tenant PII in any response or event payload (verified by test, not by eyeball).
4. Docs page renders at `/developers` in both prerender and SPA modes.
5. The Pranjal reply email can contain one docs URL and nothing bespoke.
